Developer docs

Create an order on your server, hand the checkout session to the browser, and read the authoritative payment status back on your server.

Credentials — and the base URL they work against — are issued on request: write to support@beyound.in. Overview

Beyound Checkout is a payment layer that sits between your checkout page and the shopper's bank. The integration has three moving parts:

  • Your server creates an order. One call with your secret key returns the order plus a checkout session.
  • Your page hands that session to the browser. The session token authenticates the payment sheet, which renders inline on your own checkout page — the shopper never leaves your domain to choose a method.
  • Your server reads the result. When the sheet reports back, you read the order on your server and act on that status, not on what the browser told you.

The two shopper paths

  • One tap. If the shopper has already approved a card at your brand — a standing instruction (e-mandate) they authorised once with a real bank OTP — the pay bar charges that card in place. No sheet opens, no OTP, no redirect, no bank page. This path is capped at ₹25,000 per payment.
  • Full sheet. Everyone else. The sheet opens over your checkout page with the fixed method hierarchy, and the authentication step depends on the method chosen: an in-sheet 3-D Secure code for cards, an approval in the shopper's UPI app, or a bank login for net banking.

Which calls are yours

Your server calls exactly two endpoints: POST /v1/orders to create the order, and GET /v1/orders/{orderId} to read the result. Every other endpoint on this page is called by the sheet in the browser using the session token. You do not implement those — they are documented so you know what is happening on your page.

Conventions

  • Base path /v1. Transport is HTTPS with JSON bodies.
  • Amounts are integer minor units (paise) — 910700 is ₹9,107.00. Currency is INR.
  • Timestamps are RFC-3339, UTC.
  • Identifiers are opaque, prefixed strings: ord_ for orders, cs_ for checkout sessions, pay_ for payments, pi_ for saved instruments, mnd_ for standing instructions.

Base URL. Every example on this page uses https://api.beyound.in as the host. Treat that as a labelled placeholder: the base URL your keys work against is confirmed when your preview credentials are issued.

No address step. The preview contract has no address or shipping resource. Address capture, validation and storage stay on your own checkout — Beyound only collects the money.

Authentication

There are two credential types, and they are not interchangeable. Both travel in the Authorization header as a bearer token.

Merchant secret key — server to server

Your server only
Authorization: Bearer sk_live_...

The secret key identifies your brand. It creates orders and reads them back. It is the credential behind every merchant-scoped call in the reference below.

The secret key must never ship to the browser. Not in a script tag, not in a data attribute, not in a public environment variable, not through your own API as a passthrough. It belongs on your server, in your secret store. Anything the browser can read, a shopper can read.

Checkout session token — browser and app

Browser
Authorization: Bearer cs_...

The session token is minted when an order's checkout is opened, and it is returned to you as session.client_token from POST /v1/orders. It is short-lived — it carries its own expires_at — and it is scoped to one order. It is what every client-facing endpoint on this page uses. It is safe in the browser precisely because it can do so little: it cannot create orders, and it cannot touch a different order.

Idempotency

Every POST that moves money accepts an Idempotency-Key header, and payment initiation requires one:

Header
Idempotency-Key: ord-req-8f2c1a7e
  • POST /v1/checkout/{sessionId}/payments — required.
  • POST /v1/mandates/charge — the one-tap charge, sent with an idempotency key.

The contract specifies Idempotency-Key for money-moving POSTs. Sending it on order creation too — as the quickstart does — costs nothing and keeps your retry logic uniform, but whether order creation de-duplicates on it is not yet finalised in the preview API. Do not rely on it to prevent duplicate orders; use your own merchant_reference to reconcile.

Shopper identity

The shopper is identified inside the checkout session, not by you. How that identity is established on each surface — app sign-on versus a web step — is not yet finalised in the preview API. You pass what you know about the shopper (customer.ref, name, phone) when you create the order.

Quickstart

Three steps: create, mount, confirm. The first and third are yours; the middle one is mostly the sheet's.

1

Create the order on your server

Do this when the shopper reaches your payment step, with your secret key. The response gives you both the order and the checkout session.

Request · your server
curl -X POST https://api.beyound.in/v1/orders \
  -H 'Authorization: Bearer sk_live_YOUR_SECRET_KEY' \
  -H 'Idempotency-Key: ord-req-8f2c1a7e' \
  -H 'Content-Type: application/json' \
  -d '{
    "currency": "INR",
    "amount": { "base": 814200, "tax": 96500, "total": 910700 },
    "line_items": [
      { "type": "flight", "title": "IndiGo 6E 2144" }
    ],
    "customer": {
      "ref": "cust_10482",
      "name": "R. Jain",
      "phone": "+919800003391"
    },
    "merchant_reference": "ORD-9987",
    "fare_hold_seconds": 540
  }'
  • amount — base, tax and total, all in paise. total is what gets charged.
  • customer.ref — your own identifier for the shopper. It comes back to you on reads.
  • merchant_reference — your order number. Use it to reconcile.
  • fare_hold_seconds — how long the order is held. When it elapses the order reads expired and payment attempts fail with fare_hold_expired.

The line_items example above is the shape the reference implementation exercises, which models a travel order. The full line_items schema for other verticals is not yet finalised in the preview API — confirm your item shape with support before you build against it.

Response · 201 (abridged)
{
  "order": {
    "id": "ord_123",
    "status": "created"
  },
  "session": {
    "id": "cs_9f42",
    "client_token": "cs_9f42_4c1d...",
    "expires_at": "2026-08-14T06:10:00Z"
  }
}

Store order.id against your own order record now. You will need it in step 3, and it is the only handle that survives the browser.

2

Hand the session to the browser and mount the sheet

Send session.id and session.client_token down to your checkout page — rendered into the page by your server, or returned from your own endpoint. Send nothing else. The token authenticates the sheet, which hydrates itself from the session bootstrap:

Browser · session bootstrap
// sessionId and clientToken came from your server in step 1.
// Your secret key never appears in this file.
const res = await fetch(
  `https://api.beyound.in/v1/checkout/session/${sessionId}`,
  { headers: { Authorization: `Bearer ${clientToken}` } }
);
const checkout = await res.json();

One call hydrates the whole sheet. The response carries a session block (with its expires_at), the merchant branding, the order and its amount breakdown, the customer, the instruments the shopper can pay with in their fixed order, and any offers applicable to this order. If the shopper already has an approved card at your brand, that block is present too — which is exactly what selects the one-tap path over the full sheet.

The browser embed is not published during developer preview. There is no public script tag, package name or install command for the sheet yet — do not go looking for one, and do not build against a guess. What is specified today is the session-token contract above. The embed is confirmed together with your credentials.

3

Read the final status on your server, then confirm the order

When the sheet finishes, poll the order with your secret key until it reaches a terminal status. This read is what you act on.

Request · your server
curl https://api.beyound.in/v1/orders/ord_123 \
  -H 'Authorization: Bearer sk_live_YOUR_SECRET_KEY'

The order read gives you:

  • status — one of created, paying, paid, failed, expired.
  • confirmation — present once paid. It carries the settlement reference utr and a paid_summary line you can print on a receipt.
  • fare_hold_expires_at — when the hold on this order lapses.

The sheet itself polls GET /v1/payments/{paymentId} for the in-flight payment states (pending, authorising, charging, settled, declined). That read is session-scoped and drives the UI. Your fulfilment decision should hang off the order read, with your secret key.

The server-side status read is authoritative. Never mark an order paid because a browser callback, redirect parameter or client-side success screen said so — any of those can be replayed, forged or simply lost when a shopper closes the tab. Only status: "paid" from GET /v1/orders/{orderId}, read with your secret key, releases goods.

API reference

Every merchant- and session-scoped endpoint in the preview contract, grouped by resource. Paths are relative to the base URL and already include the /v1 prefix.

Method + path Purpose Auth scope
Orders
POST /v1/orders Create the order and mint its checkout session. Merchant secret key
GET /v1/orders/{orderId} Read order status and, once paid, the confirmation. The authoritative read. Merchant key or session
Session
GET /v1/checkout/session/{sessionId} Hydrate the sheet in one call: order, merchant branding, customer, saved instruments, standing-instruction state, offers. Session token
Instruments
GET /v1/checkout/{sessionId}/instruments Re-fetch the saved instruments in their fixed hierarchy. Usually already delivered by the session bootstrap. Session token
POST /v1/checkout/{sessionId}/cards Add a new card from a network token. No card number and no CVV is stored — the card data goes to the network tokenisation endpoint and only the token reaches Beyound. Session token
Payments
POST /v1/checkout/{sessionId}/payments Initiate a payment for the method the shopper picked. Returns the payment id and the next action to perform. Idempotency-Key required. Session token
POST /v1/payments/{paymentId}/otp Submit the 3-D Secure code the shopper entered. Session token
POST /v1/payments/{paymentId}/otp/resend Re-send the 3-D Secure code. Returns the cool-down before the next resend. Session token
GET /v1/payments/{paymentId} Poll payment status, and on completion the receipt or the decline detail. Session token
Mandates — standing instructions
POST /v1/mandates/charge Charge an approved card under its standing instruction. This is the one-tap path: no additional factor, cap enforced at ₹25,000 per payment. Session token
Offers
GET /v1/checkout/{sessionId}/offers Offers applicable to this order. An empty array means the sheet shows no offer treatment at all. Session token

A standing instruction is created only as a side effect of a successful card payment where the shopper ticked the consent — the bank's additional-factor step is what registers it. There is no standalone create call. Listing and cancelling standing instructions are customer-scoped surfaces, not part of the merchant integration, so they are not documented here.

Payment methods

The sheet renders one fixed hierarchy, in this order, for every shopper. It is not personalised and not reorderable — fastest first, most likely to leave your page last.

  1. Approved card — one tap Shown only when the shopper already has an active standing instruction on a card at your brand. One tap charges it: no OTP, no redirect, no bank page. Capped at ₹25,000 per payment; above the cap the attempt fails with mandate_cap_exceeded and the shopper picks another method.
  2. Eligible saved cards Saved cards that can carry a standing instruction. They pay with one 3-D Secure code now, and — if the shopper consents at the same time — become one-tap cards for their next payment at your brand.
  3. Other saved cards Saved cards that are not eligible for a standing instruction. They pay exactly like any other card, with 3-D Secure each time; the one-tap consent is not offered on them.
  4. New card An add-card form. The card is tokenised with the network — no card number and no CVV is stored by Beyound — and authenticated with a 3-D Secure code in the sheet. The consent checkbox is intent only: the standing instruction is registered after the bank's additional-factor step succeeds, never before.
  5. UPI Expands in place to the shopper's UPI apps, or a UPI ID. Sends a collect request the shopper approves in their app, inside a fixed window.
  6. Net banking Expands to a bank list and hands off with a redirect and a return URL. Last in the order because it is the slowest and the most likely to take the shopper off your page.

What each method returns

Payment initiation answers with the payment id, a status, and a next_action describing what has to happen before the money moves. The sheet drives that action; you do not.

Method next_action.type What follows
Approved card (one tap) mandate_charge No shopper action. Poll until the payment settles.
Saved or new card otp_3ds The sheet collects the 3-D Secure code and submits it to /otp.
UPI upi_collect Collect request to the chosen app; expires_in_s bounds the wait.
Net banking netbanking_redirect Carries redirect_url and return_url for the bank hand-off.
Response · payment initiated, card path
{
  "payment_id": "pay_1",
  "status": "authorising",
  "next_action": {
    "type": "otp_3ds",
    "bank": "ICICI Bank",
    "phone_masked": "+91 ·····3391",
    "resend_after_s": 24,
    "expires_in_s": 300
  }
}

Status and webhooks

Webhooks

The preview API does not specify webhooks. There are no event names, no delivery endpoint, no signing scheme and no retry policy in the contract today — so none are documented here, and you should not design your fulfilment around a callback that does not exist yet. If outbound events matter to your integration, say so when you request credentials.

How to get status today

Status is retrieved by polling. Two reads exist, and they are for different callers:

  • Your server polls GET /v1/orders/{orderId} with the secret key. Statuses: created, paying, paid, failed, expired. Poll from the moment you hand the session to the browser until you get a terminal status or the hold expires.
  • The sheet polls GET /v1/payments/{paymentId} with the session token. Statuses: pending, authorising, charging, settled, declined. This drives the in-sheet UI — it is not your fulfilment signal.

A settled payment carries the amount, what it was paid with, and a receipt containing the settlement reference. The same outcome reaches you as confirmation on the order read.

Errors and declines

Every error uses one envelope, whatever the endpoint:

Error envelope
{
  "error": {
    "code": "card_declined",
    "message": "...",
    "retryable": true,
    "details": { }
  }
}

Branch on code, never on message — the message is written for humans and will change. retryable marks the errors where re-sending the same request can succeed.

Error codes

CodeMeaning
unauthorizedMissing, invalid, or wrong-scope credential.
session_expiredThe checkout session is past its expires_at. Create a new order.
order_not_foundNo order with that id under this key.
order_expiredThe order is no longer payable.
fare_hold_expiredThe hold window on the order elapsed before the payment completed.
card_declinedThe issuing bank declined the card. Nothing was charged.
mandate_cap_exceededThe amount is above the ₹25,000 one-tap cap. The shopper must pick another method.
mandate_inactiveThe standing instruction is no longer active — cancelled at Beyound or at the bank.
otp_invalidWrong 3-D Secure code.
otp_expiredThe 3-D Secure code lapsed before it was submitted.
upi_timeoutThe shopper did not approve the UPI collect request in time.
instrument_ineligibleThat instrument cannot be used for this payment.
validation_errorThe request body failed validation. Check details.

Declines

A decline is not an error envelope — it is a terminal payment status. The payment read comes back with status: "declined" and a decline object:

Response · declined payment (abridged)
{
  "status": "declined",
  "decline": {
    "reason": "Your bank declined the card. Nothing was charged.",
    "fare_hold_expires_at": "2026-08-14T06:19:00Z",
    "retry_suggestion": "Try UPI or another card"
  }
}
  • A decline means nothing was charged. No money left the shopper's account, so there is nothing to reverse and no refund to issue.
  • A declined payment registers no standing instruction. If the shopper consented to one-tap on a card that then declined, the consent does not take effect — the bank's additional-factor step is what registers it, and it did not succeed.
  • The order stays payable until fare_hold_expires_at. The sheet offers a retry with a different method inside that window; your order record should not be cancelled the moment one attempt declines.

Testing and going live

Beyound Checkout is in developer preview, and the honest version is short: onboarding is a conversation, not a sign-up form.

  • Credentials are issued on request. Write to support@beyound.in with your brand and the domains your checkout runs on. Your secret key, the base URL it works against, and the browser embed are issued together.
  • There is no published sandbox. No test base URL and no test card numbers are part of the preview contract. Do not construct your own against a guessed host.
  • There are no webhooks yet. Build the server-side poll from the start — see the status section above.
  • Everything not on this page is unspecified. Rate limits, settlement timing, commercial terms and the browser embed are not in the preview API contract. Ask; do not assume.

Two things are worth getting right before you write any code, because they do not change when the preview does: keep the secret key on your server, and treat the server-side order read as the only thing that marks an order paid.
