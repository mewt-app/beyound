Beyound Checkout

A hosted payment sheet. Render it on your checkout page; buyers pick a card, UPI, net-banking, or a saved “bolt” and pay. Beyound handles PG routing, 3DS OTP, saved-card tokenization, and settlement.

Version August 2026 API base https://api-v2.superpe.in Checkout host https://checkout.rallyapp.in

What this is

Beyound Checkout is a hosted payment sheet. You render it on your checkout page; buyers pick a card, UPI, net-banking, or a saved “bolt” and pay. Beyound handles the PG routing, 3DS OTP, saved-card tokenization, and settlement — end to end, inside the sheet.

Your side of the integration is two things:

  • Server — create an order → get back a session token.
  • Browser — render the Beyound checkout sheet with the session token; the buyer pays inside it.
Source of truth

The webhook comes last and is authoritative. Everything else is UI.

Getting a brand key

Beyound ops provisions you a brand row (brand_…) internally. You receive three things over a secrets channel:

  • sk_live_… — server-to-server secret. Send as Authorization: Bearer sk_live_…. Never expose to the browser.
  • sk_sandbox_… — sandbox counterpart. Same API, sandbox=true on the row.
  • webhook_secret — HMAC-SHA256 key. You verify inbound webhooks with this.
Key handling

Beyound stores only sha256(sk_…) on our side. If you ever lose the raw key, we mint a new one and disable the old — no lookup, no recovery.

The brand row also holds:

  • allowedOrigins — the origins allowed to render the checkout sheet (e.g. https://your-store.com,https://www.your-store.com).
  • webhookUrl — where Beyound POSTs terminal events.

Auth

Every server request carries:

http
Authorization: Bearer sk_live_<random>
Content-Type: application/json
Idempotency-Key: <uuid>            # recommended on POSTs

Your sk_ key fully identifies your brand — every order is bound to it automatically. There’s nothing else to send for identity.

The checkout sheet uses a short-lived cs_… session token, not the sk_…. That token is minted for you inside the create-order response — see the next section.

End-to-end flow

  1. Your backend → Beyound. POST /api/v1/orders with the cart total.
  2. Beyound → your backend. Response has an order.id (ord_…) and a session.clientToken (cs_…).
  3. Your backend → browser. Ship the cs_… token down to the checkout page.
  4. Browser renders the Beyound checkout sheet. Point the sheet at the session token — Beyound serves the payment UI from the checkout host.
  5. Buyer pays inside the sheet. Beyound routes the transaction to a PG and walks the buyer through 3DS, OTP, and any bank redirects — all handled inside the sheet.
  6. Beyound → your backend. Webhook (order.paid or order.failed) hits webhookUrl with an HMAC signature. This is authoritative. Only mark your order as paid after this fires and the signature verifies.
Trust the webhook

The sheet shows the buyer a confirmation the moment payment settles, but your order state must only flip on the webhook. If the buyer closes the tab after paying, the webhook still delivers.

Webhooks

Terminal events POST to your webhookUrl with these headers:

HeaderValue
X-Rally-Eventorder.paid, payment.captured, order.failed, or payment.declined.
X-Rally-DeliveryUUID. Unique per delivery attempt. Use this as your dedupe key.
X-Signaturehex(hmac_sha256(webhook_secret, raw_request_body))
X-TimestampUnix seconds. Reject if |now − X-Timestamp| > 300.
Verify before you parse

Verify the signature before parsing the body. Constant-time compare (hmac.compare_digest in Python, crypto.timingSafeEqual in Node, MessageDigest.isEqual in Java).

Retries on non-2xx: 30s → 5m → 30m → 3h → 12h → 24h. Six attempts, then we mark the row failed and stop. Respond 2xx fast (< 3s), do the actual work async.

Events (today)

  • order.paid — order flipped to paid.
  • payment.captured — a payment attempt reached settled.
  • order.failed — order flipped to failed.
  • payment.declined — a payment attempt reached declined.
Roadmap

mandate.activated, mandate.cancelled, refund.processed are on the roadmap. We’ll announce before enabling them.

Idempotency

Two layers:

  • Order-level. merchantReference is unique per brand in Beyound’s DB. Retrying POST /orders with the same merchantReference returns the existing order and a fresh session. Never duplicates.
  • Request-level. Set Idempotency-Key: <uuid> on any POST. Beyound caches the response for 15 minutes keyed by (brandId, endpoint, idempotencyKey, body_md5) and replays it verbatim on retry.
Best practice

Send an Idempotency-Key on every POST and a merchantReference on POST /orders.

Sandbox

There isn’t a separate sandbox host yet. Provision a brand with sandbox=true and you’ll get an sk_sandbox_… key that hits the same base URL as prod but is logically isolated by the flag.

Test cards / UPI VPAs are not yet Beyound-owned. Charges route to the underlying PG’s own test mode (Razorpay test MID, etc.), so use whichever test data your PG documents. When Beyound’s dedicated sandbox lands, we’ll ship a matrix in this document.

Beyound Cash

Buyers earn Beyound Cash on eligible checkouts. It shows up as a reward in the checkout sheet and, if the buyer has the Beyound app installed, in their app balance. Nothing for you to integrate — it’s inside the sheet. Documented here so the reward line-item in the receipt isn’t a surprise.

Go-live checklist

  • Beyound ops provisioned your prod sk_live_… + webhook_secret.
  • Your prod origin(s) are in the brand’s allowedOrigins.
  • Webhook endpoint is HTTPS, verifies the HMAC signature before parsing, responds 2xx in < 3s.
  • Idempotency tested: same merchantReference fired twice → single order in your system.
  • Webhook wired: order.paid / order.failed is what actually flips your order state.
  • One card 3DS success + one card 3DS decline tested on sandbox.
  • One UPI success + one UPI decline tested on sandbox.
  • Your PCI review is comfortable: raw PAN, CVV, OTP never leave the Beyound checkout sheet.

Appendix C — Verifying a webhook (Node)

javascript
const crypto = require('crypto');

app.post('/beyound/webhook', (req, res) => {
  const raw       = req.rawBody;                            // raw utf-8 bytes
  const supplied  = req.headers['x-signature'];
  const timestamp = Number(req.headers['x-timestamp']);

  if (Math.abs(Date.now() / 1000 - timestamp) > 300) {
    return res.status(401).send('stale');
  }

  const expected = crypto
    .createHmac('sha256', WEBHOOK_SECRET)
    .update(raw)
    .digest('hex');

  if (!crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(supplied))) {
    return res.status(401).send('bad signature');
  }

  // Dedupe on X-Rally-Delivery, then handle req.body.event
  res.sendStatus(200);
});
